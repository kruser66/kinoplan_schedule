# Ревью MR `wiki_mvp` → `master`

Ветка: `wiki_mvp` (18 коммитов, 47 файлов, +1883/−148). Прод = `master`, MR не смёржен.

## Сводка

Крупный, в целом аккуратный MR: новое приложение `wiki` (модели Category/Tag/Article,
markdown+bleach рендер, поиск через денормализованный `search_text`, портал, демо-сид
миграцией) плюс зачистка хозяинства в `schedule` (просмотр недели больше не создаёт
записи, unique (год, неделя) + миграция-склейка, автоочистка картинок >30 дней по
`user_logged_in`). Осознанные решения (кириллические слаги, search_text под SQLite,
lazy-импорт в apps.py, импорты моделей внутри миграций) проверены и не оспариваются.
XSS-защита рендера корректна (bleach:cscript/скрипты вырезаны, протоколы href/src
фильтруются дефолтными `allowed_protocols`; есть тест). Права: чтение — LOGIN_REQUIRED,
запись/бэкап — staff (`can_edit`, тесты на 403/скрытие кнопок). Критичных находок нет;
две средние и семь низких, перечислены ниже.

**радиус: 14 мест, проверено 14** (MEDIA_* fix: `schedule/urls.py:12` static() — только
DEBUG, `image.url` в `templates/index.html`, `.env` прочитан — ключей STATIC_*/MEDIA_*
нет, поведение не меняется; new deps markdown/bleach: единственный потребитель
`wiki/render.py` → `wiki/views.py:114`, версии 6.4.0/3.11.3 существуют и установлены,
на фронте JS-потребителей нет; shared `templates/base.html`: 3 расширника home/index/
login; смена семантики `index`: 2 ссылки `{% url 'index' %}` + LOGIN_REDIRECT_URL='/' +
тесты; UniqueConstraint Schedule: единственный создатель записей `schedule/views.py:48`
(POST), покрыт тестом; search_text: save/backfill/search/admin — админка не покрыта, это
находка W-1). **Не проверено:** конфиг nginx (вне репо; DEPLOY заявляет «без изменений»),
фактический прогон dedupe-миграции на 117k реальных прод-строк (по коду идемпотентно,
данные недоступны).

## Замечания

### W-1. Medium — поиск в админке вики не работает с кириллицей на проде (SQLite)

`wiki/admin.py:11,28` — `search_fields = ['title', 'body']` / `['name']`. Django admin
без явного lookup подставляет `__icontains` (`django/contrib/admin/options.py:1218`),
а MR ровно поэтому отказался от `icontains` в пользовательском поиске: SQLite `UPPER()`
не казеит кириллицу. На проде поиск по статьям в списке админки будет искать только
латиницу/цифры — для полностью кириллической вики фактически мёртв.
Почему: единственный инструмент, где редактор ищет статью «по чему помнится» до
открытия, — админский список; staffers получат «не находит ничего» при живом фронтенд-поиске.
Аналоги: `wiki/models.py:102-107` (search_text в нижнем регистре при save) и
`wiki/views.py:83` (`search_text__contains=query.lower()`) — как у них; админка от
паттерна отвалилась. Просьба: распространить тот же паттерн на админку (напр.
`search_fields` через `search_text` + кастомный `get_search_results` c lower() запроса,
или `search_text__contains` c понижением регистра в запросе).

### W-2. Medium — тяжёлая синхронная чистка в запросе логина; `created_at` без индекса

`schedule/apps.py:9-18` (сигнал на каждый `user_logged_in`) → `schedule/cleanup.py:34`
(`filter(created_at__lt=cutoff)` — поля без `db_index`, `schedule/models.py:25`) +
`cleanup.py:20` (count пустых недель). На проде до чистки ~117k строк: если после
`migrate` раньше ручной команды залогинится любой пользователь, чистка тысяч картинок
с файловой IO выполнится внутри запроса входа → gunicorn worker таймаут и «сайт лёг при
входе». После ручной чистки сигнал остаётся дешёвым, но сканирует всю таблицу картинок
каждый логин. Почему: вход кассира — критичная операция для смены; DEPLOY рекомендует
сначала команду, но не гарантирует порядок (health-чек/первый вошедший обходят рекомендацию).
Просьба: сделать первый заход безопасным — добавить индекс на `created_at` и/или ранний
выход без петли (если «старых» нет — ничего не удаляем), опционально порог/троттлинг.

### W-3. Low — миграция `0002` содержит мёртвый backfill

`schedule/migrations/0002_scheduleimage_created_at.py:6-16` фильтрует
`created_at__isnull=True`, но AddField с `auto_now_add` выставляет существующим строкам
«сейчас» на уровне schema editor (проверено в локальном Django:
`db/backends/base/schema.py:474` `_effective_default`) — фильтр не матчит ни одной строки,
RunPython ничего не делает. Реальный бэкфилт — в 0003 (её докстринг это и описывает).
Почему: вводящий в заблуждение мёртвый код в цепочке миграций, которые ревьюят построчно;
следующий читатель будет гадать, какая из двух «настоящая». Просьба: убрать RunPython из
0002 (или перекомментировать, что он — страховка от семантики NULL). Данные не страдают:
0003 перекрывает.

### W-4. Low — счётчик `missing` в чистке недостижим

`schedule/cleanup.py:43-47`: при отсутствующем файле `default_storage.exists()` даёт False,
`delete` не вызывается, но `result['files'] += 1` выполняется всё равно — удалённые
«воздухом» картинки считаются удалёнными файлами, `missing` не растёт никогда (except
недостижим кроме гонки). Почему: Dry-run/отчётность чистки врёт о числе реально удалённых
файлов — человек по логам оценит освобождённое место неверно. Просьба: инкрементировать
`missing` в ветке «не exists», `files` — только после успешного delete.

### W-5. Low — поиск не экранирует `%` и `_`

`wiki/views.py:83`: `search_text__contains=query.lower()` — Django не экранирует
LIKE-джокеры (официально документированное поведение): запрос «100%» найдёт всё, где после
«100» есть хоть что-то, одиночный «%» выдаст все статьи. Почему: пользовательский поиск
по инструкциям с процентами («наценка 50%», «_» в именах файлов) вернёт мусор вместо
совпадений — тот же класс «тихого» бага, что и кириллица с icontains. Просьба: экранировать
джокеры (Value c кастомным escape или замена `%`→`\%`, `_`\_` перед фильтром).

### W-6. Low — нет защиты от цикла parent у Category

`wiki/models.py:34-37` (save) — можно назначить `parent` потомком себя; дальше
`breadcrumbs()` (`models.py:45-51`) и `children_deep_count()` (`models.py:53-58`) —
бесконечная рекурсия → RecursionError/500 на любой странице с деревом (сайдбар есть везде),
чинить придётся через DB. Почему: одна оплошность админа в form-шке «родитель» кладёт всю
вики, включая расписание-портал (tree рендерится в сайдбаре wiki; portal — нет, но вики —
да). Просьба: проверка восходящей цепи в `Category.clean()`/save (parent не среди потомков).

### W-7. Low — `schedule` стал зависим от `wiki` ради счётчиков портала

`schedule/views.py:12` — `from wiki.models import Article, Category` только для двух
count'ов на портал (`views.py:19-25`). При удалении/переименовании вики приложение
расписания падает на импорте. Просьба: развязать (инлайн-запросы через `apps.get_model`
или перенос портала в нейтральное место/корневые url) — либо осознанно оставить и
зафиксировать зависимость в DEPLOY/README.

### W-8. Low — откат миграции 0005 удалит не-демо сущности с теми же именами/sлагами

`wiki/migrations/0005_seed_demo.py:1421-1427` (unseed): удаляет категории по
`DEMO_CATEGORY_SLUGS` и теги по именам. Если до откатa админ создаст свою «Кассу»/тег
«касса» — они попадут под удаление; `DEMO_ARTICLE_SLUGS` предполагает, что слагами не
разошлись (`_slug` при конфликте добавит `-2`, и демо-статья переживёт откат). Почему:
процедура откатa из DEPLOY (§6) на живой базе может тихо снести пользовательские данные;
идемпотентность forward не покрывает это. Просьба: фильтровать по признаку демо (напр.
author=admin + exact-слага с fallback-списком «-2» вариантов, или префикс в имени/слаге).

### W-9. Low — DEPLOY.md: устаревшие детали откатa и описания миграций

`DEPLOY.md` §6: «migrate wiki 0001 # откат wiki-миграций (0004->0001)» — миграций уже
пять (0005 с демо-сидом тоже откатится; см. W-8 про последствия). §5 чеклист «5 категорий
… 6 статей … 9 тегов» не сходится с кодом 0005 (категорий с welcome — 6, статей — 6 +
welcome = 7). Просьба: привести цифры/диапазон откатa к фактическому состоянию ветки,
иначе чеклист после деплоя «не бьётся» и дежурный решит, что сид сломался.

### W-10. Low (pre-existing, НЕ из этого MR) — `delete_image`: GET-удаление, `@csrf_exempt`, голый `except: pass`

Проверено `git diff master...wiki_mvp -- schedule/views.py`: функции нет в диффе —
дичает с мастера (ссылка-удаление GET'ом, CSRF-исключение, проглоченные ошибки; у

## Описание MR (для автора/рецензентов)

Ветка добавляет приложение вики (статьи/категории/теги, markdown-рендер с санитизацией,
поиск без зависимости от SQLite-специфики, портал /, страница профиля и выгрузка БД для
staff) и лечит деградацию расписания: 117k «бирок» недель от просмотра-с-записью (read-
only GET + unique (год,неделя) + склейка), бесконечный рост картинок (автоочистка >30 дней
при логине + команда). Деплой-процедура расписана в DEPLOY.md, демо-контент сеится
идемпототентной миграцией. Основные риски сосредоточены не в коде вики, а в операционке:
порядок «миграция → ручная чистка → первый логин» (W-2) и откат демо-сида (W-8).

## Не проверено

- Реальный прогон `schedule 0004` (dedupe) на прод-данных — только аудит кода миграции.
- `.env` прод-сервера напрямую: прочитан `.env` в рабочем каталоге (он же путь из DEPLOY.md);
  если прод живёт на другой машине — перепроверить отсутствие STATIC_*/MEDIA_* ключей.

- Покомнатная сверка CSS (`wiki.css`) с прототипом — не предмет ревью.

## Комментарии для тредов MR

**W-1 (Medium)**
`wiki/admin.py:11,28` — `search_fields` в админке статей/категорий пойдут через `__icontains`, который на SQLite-проде не казеит кириллицу: поиск в списке админки по русской вики будет находить только латиницу. Просьба: распространить на админку тот же lower-паттерн, что уже сделан для фронтенд-поиска (`search_text` + `lower()` запроса, как `wiki/views.py:83`).

Почему: админский список — единственное место, где редактор ищет статью «по памяти» до открытия, и она окажется мертва на том же прод-движке, под который весь MR и обходил SQLite (wiki/admin.py:11).

**W-2 (Medium)**
Сигнал на логине (`schedule/apps.py:9`) синхронно чистит картинки; на проде до ручной чистки это тысячи удалений с файловой IO внутри запроса входа, плюс фильтр `created_at__lt` без индекса (`schedule/models.py:25`) сканирует всю таблицу картинок при каждом логине. Просьба: сделать вход неуязвимым — индекс на `created_at` и ранний выход из `cleanup_old_images`, когда старых записей нет.

Почему: если после `migrate` раньше админской команды залогинится любой сотрудник, вход уйдёт в worker-таймаут — «сайт не пускает на смену» в первый же день деплоя.

**W-3 (Low)**
`schedule/migrations/0002…:6-16` — `backfill_created_at` фильтрует `created_at__isnull=True`, но AddField с `auto_now_add` заполняет существующие строки «сейчас» (Django `_effective_default`), так что RunPython никогда ничего не находит; реальный бэкфилт — в 0003. Просьба: убрать мёртвый RunPython из 0002 или явно перекомментировать его роль.

Почему: цепочку 0002/0003 ревьюят и будут ревьюить построчно; мёртвый код с правдоподобным докстрингом заставляет сомневаться, какая из миграций «настоящая».

**W-4 (Low)**
`schedule/cleanup.py:43-47` — при отсутствующем файле ветка `missing` недостижима: после `exists()==False` всё равно идёт `files += 1`. Просьба: считать `missing` в ветке «файла нет», `files` — только после успешного удаления.

Почему: dry-run и финальный лог — единственный способ оценить реально освобождённое место; сейчас отчёт завышает число удалённых файлов и никогда не покажет «уже отсутствовали».

**W-5 (Low)**
`wiki/views.py:83` — `search_text__contains` не экранирует LIKE-джокеры `%` и `_`: запрос «50%» найдёт всё, где после «50» есть любой текст, «%» один — все статьи. Просьба: экранировать джокеры перед фильтром.

Почему: инструкции про цены/наценки полны процентов — пользователи увидят «найдено всё» вместо точных совпадений, тот же тихий класс бага, что чинили с кириллицей.

**W-6 (Low)**
У `Category` (`wiki/models.py:34`) можно выставить `parent`-цикл (потомок → предок); после этого `breadcrumbs()`/`children_deep_count()` — бесконечная рекурсия и 500 на любой странице вики с сайдбаром. Просьба: запретить цикл в save/clean с внятной ошибкой админки.

Почему: одна ошибка при перекладывании категории в админке кладёт всю базу знаний и требует починки напрямую через БД (wiki/models.py:45,53).

**W-7 (Low)**
`schedule/views.py:12` импортирует `wiki.models` ради двух count'ов портала — приложение расписания теперь не живёт без вики. Просьба: развязать (`django.apps.apps.get_model` на месте или перенос счётчиков из `schedule`) либо зафиксировать зависимость в README/DEPLOY.

Почему: будущее вычёркивание/перенос вики из settings уронит импорт `schedule.views` на старте gunicorn — падение неочевидно диагностируется (schedule/views.py:12).

**W-8 (Low)**
