# План: вики для кинотеатра (черновик обсуждения)

Дата обсуждения: 2026-11-05. Статус: обсуждение вариантов, код не писан.

## Контекст проекта
- Django 5.2 (SQLite), gunicorn -w 2, VDS ~1 ГБ RAM, авторизация django.contrib.auth, вход в /admin/.
- Ограничения: мало памяти — тяжёлые движки (Wiki.js, Outline, django-wiki, Wagtail) не вариант.

## Решение (договорились)
Вариант 1: приложение `wiki` внутри текущего Django-проекта. Плюс надстройка API/бот позже.

### MVP (1-2 вечера)
- app `wiki`
- модели: `Category` (дерево разделов, django-treebeard MP_Node, breadcrumbs) + `Article` (title, slug, category, body markdown, is_draft, created/updated, author)
- рендер markdown: библиотека `markdown` (+ опционально django-martor для редактора с превью)
- чтение — для залогиненных; правка — в Django admin (редакторы = staff)
- шаблоны: список разделов, страница статьи, breadcrumbs

### Этап 2
- поиск (icontains по title/body, позже SQLite FTS5)
- история правок (django-simple-history)
- вложения (картинки в media/, уже настроено)

### Этап 3 (опционально)
- JSON API: /api/wiki/search/?q=, /api/wiki/article/<slug>/
- Telegram-бот поверх тех же данных

## Отклонённые варианты
- BookStack — похож на Confluence, но PHP+MySQL отдельным сервисом ~200MB RAM — риск OOM на этой VDS. Только на отдельном сервере.
- django-wiki — тяжеловат и маложивучий.
- Wagtail — тяжёлая CMS, только при сценарии «сайт+вики+новости» целиком.
- django-flatpages — как ultra-MVP без дерева/версий.

## Открытые вопросы (ждать ответов пользователя)

2. Правки: достаточно Django admin или нужен редактор прямо на сайте (martor/textarea+превью)?
3. Нужна ли история правок (кто/когда менял)?
4. Группы доступа: одна общая вики с разделами или разграничение по ролям («касса видит только своё»)? -> если разграничение, думать про django-guardian (object-level perms) вместо штатных групп.
